# sim-viewer — 全体設計（日本語ダイジェスト・非正本）

> **正本は `specs/` 配下の英語仕様**。差異があれば英語版が正しい。ここは全体像をつかむための要約で、
> 決定の根拠・条文・受入基準は正本にある。

## 何をする製品か

CAE の結果ファイル（.vtu / .cgns / .foam / .case など）を読み込み、**受け手が何もインストールせずに
開ける、完成した成果物**を作る。形状・単位付きの数値・グラフ・考察・合否が1つのファイルに揃い、
人がシーンを組み立てなくても生成される。デスクトップ優先・オフライン完結。

**売り物は「正しい数値」**である。間違った値を自信満々に見せることは、機能が足りないことより悪い。
仕様の規則のほとんどはこの一点から出ている。

## 4つの作業領域

ワークスペースの木と選択中のケースは、領域を切り替えても変わらない。領域の切替は
「対象の切替」ではなく「道具の切替」。

| 領域 | 何をする |
|---|---|
| **View** | ケースを 2D / 3D で可視化する |
| **Graph** | フィールド値から図を作る |
| **Report** | 成果物を組み立てる |
| **Chat** | 自然言語で操作し、質問する |

## データの構造

**Workspace（ワークスペース）** > **Case（ケース）**（多重階層）+ **Variable（変数）**。
変数は親で宣言し、子は「継承」か「上書き」のどちらかを記録する — **子に値をコピーしない**。
継承は保存時に焼き込まれず、読み込み時に解決される。だから親を1つ変えれば継承している子が全部変わる。

**View / Graph / Report / Simulation はワークスペースに属する「テンプレートそのもの」**であり、ケースに
紐づかない（XC-109）。各作業領域の中央は**その種類のテンプレート一覧**で、切り替えも新規作成もそこで行う。
開いているテンプレートは、選択中のケース（パイプライン実行時は対象セット）に対してレンダリングされるので、
ケースを切り替えると**同じビューが描き直される**。

したがって**ケースBを見ながらビューを編集すると、テンプレートが変わり、ケースAの見え方も変わる**。これは
意図した挙動で、だからこそ4つの領域すべての右サイドバーに**「テンプレートとして保存」**がある — 変種は
偶然の分岐ではなく、意図して作るものにした。

スコープは4つ: **sample**（同梱・その場では編集不可）／**workspace**（そのワークスペースに入り、ファイルを
送れば一緒に届く）／**shared**（このマシンの全ワークスペースで使える。ワークスペースに縛られない）／
**ファイル書き出し**（人・マシンをまたぐ）。**スコープ間の移動はコピー**なので、共有ライブラリに上げても
元のワークスペースは単体で開ける。

書き出しは**依存アセットを埋め込んだ自己完結の1ファイル**。ただし再配布不可のライセンスのアセットは
埋め込まず、**名前で「要求」として列挙**する。そして共有・書き出しの時点で、そのテンプレートが
**相手側に何を要求するか**（フィールド名・単位・変数名・パーツ名・依存エントリ）を書き出す — 元の
ワークスペースでは暗黙に解決していた参照が、ここで明示になる。**昇格自体は拒否しない**、暗黙を明示に
変えるだけ。適用時は解決できたところまで適用し、できなかったものを一覧で返す（XC-090）。

テンプレートは**1ケース向け／複数ケースまたぎ／どちらでも**を宣言する。5ケースを比較するグラフは本質的に
複数ケースまたぎで、1形状のビューはそうではない。宣言してあるから、パイプラインが推測せずに済む。

保存されるのは**定義であって結果ではない**。View はフィールドの識別子とカラーマップの名前を持ち、
値もピクセルも解決済みの色スケールも持たない。ここから3つが導かれる:

- **再現性** — 保存したワークスペースを開き直すと、キャッシュではなく計算が再現される
- **安全性** — 識別子と列挙値だけの構造には評価器が無いので、LLM 生成物が脱出する先が無い
- **拡張性** — 新しい表現形式は「列挙値1つ + ハンドラ1つ」で、呼び出し側は変わらない

## システム構成（縦割り × 横割り）

**縦割り = ケイパビリティ**、**横割り = 依存方向**。画面領域は境界ではない。

横割りは上から `ui > ui-logic > state > client > service > engine > domain-core` で、**依存は下向きのみ**。
`domain-core` は何にも依存せず、ファイル・デバイス・時計に触れる処理を持たない。

縦割りは14モジュール: `domain-core` / `dataset-io` / `visualization` / `analysis` / `graph` /
`report` / `workspace` / `assistant` / `app-shell` / `shared-ui` / `pipeline` / `command` / `scripting` / `egress`。

`command` は当初 `assistant` の一部だった。だがそうすると、パイプラインもヘッドレス実行も指示バーも、
**ボタンを1つ押すために言語モデルのモジュールに依存する**ことになる。呼び出し側が複数ある面はモジュールで
あり、呼び出し側の1つが所有する面は、いずれ依存の向きを直す羽目になる面である。

**この境界は散文ではなく検査である。** `validate/check_boundaries.py` が仕様の MOD 項目を読み、
①全ファイルが正確に1モジュールに属すか ②上向き依存が無いか ③`depends_on` に無い import が無いか
を検査する。**レビュー範囲とデグレ波及範囲は、そのモジュールを `depends_on` に持つ側の集合**で決まる。

デスクトップ版と Web 版は「`service` にどう届くか」だけが違う。デスクトップはループバック上の
ローカルプロセス、Web はリモート。**`client` より上のモジュールはどちらか知らない** — 知った瞬間に
2つの製品が分岐し、全機能を二度作ることになる。

## パイプライン（ケースより上）

パイプラインは **@Workspace に登録された繰り返し手順**であり、ケースより上位の概念。**simulation は不要** —
ワークスペースに既にあるケースが出発点で、ソルバからケースを生む simulation ユニットは後のリリースで
「増える」だけ。左サイドバーで**編集する**もので、実行履歴の表示ではない。

### 実行モデルは「対象セットの蓄積」1つだけ

実行中に持つ状態は **対象セット**（GL-026）ただ1つ。

| ユニット | 実行への作用 |
|---|---|
| ケース追加 | 対象セットに**足す**（複数選択をドロップすると、**1つの**ユニットにまとまる） |
| 解析データ削除 | 対象セットを**空にし**、そのケースが読み込んでいたデータを解放する |
| view / graph / report / export / tag | **その時点の対象セット全部**に対して実行 |
| loop | 中のユニットを、**開始前に確定した回数**繰り返す |
| variable / formula | 名前に値を束縛する（下のユニットから見える） |
| condition | 式が真のときだけ中のユニットを実行 |

view ユニットは「直前のケース追加」ではなく「**それより上で足された全部**」を対象にする。だから
**ケースを1つ増やす作業は、1ユニットの編集で済む** — 下のユニットを全部直す必要がない（XC-099）。

対象セットは見えないと分からないので、**各ユニットが「何ケースに効くか」を表示する**。

### ループ・変数・数式・条件分岐の線引き

以前の版は「パイプラインは計算しない」と書いていた。これは**取り消した**。「5通りの流入速度それぞれで
回す」は、この製品の利用者が普通にやるパラメータスタディであり、それが書けないのは仕様の欠陥である。

引き直した線は「計算するかどうか」ではなく「**言語の後ろにインタプリタがあるかどうか**」:

- **ループは境界付き。** 回数は開始前に確定する（リテラル・変数の値の並び・対象セットのケース数）。
  `while` も break も無い。理由は1つで十分 — **回数が事前に決まらないとドライランが書けない**。
  そして「壊す前に見せる」（XC-094）はドライランの上に立っている。Blender の Repeat Zone も同じ制約
  （[Repeat Zone](https://docs.blender.org/manual/en/latest/modeling/geometry_nodes/utilities/repeat_zone.html)）
- **式は制限言語。** 四則・比較・論理・三項・数学関数・変数参照だけ。属性アクセスもインポートも
  関数定義も書き込みも無く、**Python インタプリタを通さない**この製品自身の評価器で評価する。
  Blender の "Simple Expressions" が同じ設計で、スクリプト実行を無効にしていても評価される
- **単位は式を通って伝播する。** 長さ ÷ 時間は速度になり、長さ + 時間は両方の単位を名指して拒否する

## Python で書く（AI ネイティブ）

**Python はドキュメントを組み立てるのであって、パイプラインそのものにはならない**（XC-102）。

- ワークスペースを開いても、何も実行されない。保存されたパイプラインを走らせても Python は動かない
- スクリプトの変更は**全部コマンド面（CT-002）を通る**ので、ログに残り、**1ステップで undo でき**、
  ドライランもできる。参考にした Blender は逆で、Python から呼んだオペレータは既定で undo を積まない
  （性能のため）。40個のレポートをエージェントに作らせた顧客が取り消せないのは困るので、ここは変える
- **無人実行は既定でオフ**。ワークスペース単位で有効化する。参考製品は寛容な既定を先に出して、後から
  オフ既定の設定を足す羽目になった

### 参照ルール（ソフト全体で1つ）

スクリプトと式から到達できるものは、**安定した識別子**と**種類の中で一意な名前**を必ず持つ。

- **保存される参照は識別子。** 名前ではない。だから改名しても何も壊れない
- **名前での検索は、1つに解決するか、失敗する。** リストを返して呼び出し側に選ばせない
- **名前の重複は、サフィックスを付けずに拒否する**（既に持っている側を名指しする）

参考2製品はここで割れている。片方は `Cube` を黙って `Cube.002` にするので、その名前で書いたスクリプトは
別のものを掴む。もう片方は重複を許して全一致をリストで返すので、公開例では `[0]` を取って祈っている
（公式ドキュメント自身が「名前が一意なときだけ堅牢」と書いている）。**拒否だけが、参照を黙って
別のものに向けない。** 出力が「名前の付いた数値」である製品では、違うオブジェクトは違う答えである。

詳細は [specs/13_scripting.md](specs/13_scripting.md)。

## レポート文の基準（LLM に書かせる前提の契約）

レポートの文章は言語モデルが書く。だから「どう書かせるか」ではなく **「技術者が何を理由にレポートを
突き返すか」** を先に仕様として書いた（[specs/14_reporting_standards.md](specs/14_reporting_standards.md)）。
プロンプトに書くのではなく、**生成後に検査する**（XC-104）。プロンプトはテストできないが、検査はできる。

### すべての文が答えるべき4つの問い

①**値はいくつか**（単位付き、または「単位未宣言」の印）②**どこまで精確か**（保存精度が支える桁まで）
③**誤差について何が分かっているか**（分からないなら「定量化していない」と書く。沈黙は「厳密」という主張）
④**どこから来たか**（データ読取／ここで計算・式を表示／参考資料・文献名／ユーザーの申告）。

**4つに答えられない文は書き直し1回、それで駄目なら落とす。** 落とすのは正しい結果である。読みやすいが
1文追跡できないレポートより、短くて全部検証できるレポートの方が価値が高い。落とした件数は本文に書く。

### 禁止する言い回し（カテゴリで規定）

ISO/IEC/IEEE 29148 と INCOSE が「検証不能になる語」として列挙しているものをそのまま使う: **最上級**
（best/optimal）、**主観語**（良好な一致・妥当・満足のいく）、**曖昧な副詞形容詞**（有意な・かなり・
わずかに・概ね）、**定量化されない比較**（〜より良い・改善した）、**逃げ道**（可能であれば・必要に応じて）、
**感情・宣伝的な語**（印象的な・劇的な・懸念される）、**偽の精度**、**ソルバの擬人化**（収束しようとした）。

特に「**有意な**」。技術文書の下書きで最頻出であり、統計的な意味を持つのに、文はその意味を意図していない。
差は**大きさと不確かさ付きで書く**か、書かないかのどちらかである。

> 「圧力損失は有意に改善した」ではなく
> 「圧力損失は 1.24 kPa から 0.98 kPa へ、0.26 kPa（21%）低下した。これらの値の離散化不確かさは
> 定量化していない。」— 後者だけが、読み手が**反論できる**文である。

### 用語の規律（V&V）

`verification`（方程式を正しく解いたか）と `validation`（正しい方程式を解いたか）は別の問いで、モデルは
日常英語の感覚で混ぜる。**検証**は数値誤差の推定がある時だけ、**妥当性確認**は不確かさ付きの実測がある時
だけ、**収束**は基準と値を明示した時だけ、**グリッド非依存**は3段階以上の細分化がある時だけ、**正確**は
同じ文に許容幅がある時だけ書ける（XC-107）。ASME V&V 20 では妥当性確認は**合否判定ではない**ので、
「validation に合格」とは書かない（ユーザーが閾値を定義した場合のみ、その閾値を名指して書く）。

不確かさは NIST TN 1297 の作法に合わせる: **包含係数 k を明示**するか合成標準不確かさを書く。信頼水準が
95%/68% と大きく異なるなら明記。**「情報は少なすぎるより多すぎる側に倒す」**。安全側に不確かさを水増し
しない（水増しした値は、態度の良い誤った値である）。

### 引用はモデルに**書かせない**。選ばせる

引用は必ず「製品が実際に取得して保持している文書」に解決する。モデルには候補一覧を渡し、**識別子で
選ばせる**だけで、参考文献を文字列として出力させない（XC-105）。裏付けが一覧に無い主張は落とす。

根拠となった実測: ある統制実験でフロンティアモデルの引用の **19.9% が完全な捏造**、13モデルのベンチマーク
では捏造率 14〜95%。決定的なのはそこではなく、**主要国際会議の2025年採択論文の約1%に捏造引用が残った —
1本あたり3〜5人の専門家査読を通過して**という事実である。専門家レビューはこの種の誤りを止められない。
だから機械的に封じるしかなく、機械的に効く唯一の方法が「参考文献を自由記述にしない」ことだった。

## Web 検索は「権限」（既定オフ）

解析・工学の知識を全部事前に持つのは不可能なので検索前提にする。ただし**ローカル完結環境が対象**なので、
検索は機能ではなく**権限**として設計した（XC-106）。

- **既定はオフ。ワークスペース単位**で有効化する。グローバル設定は間違い — ノートPCは顧客の隔離網と自宅を
  行き来するのに、境界で誰も設定を変えないから
- 設定に含むもの: 検索の可否／到達してよいホストの許可リスト／毎回確認するか
- **クエリ自身が外に出るデータ**である。送信前に何を送るか表示し、ワークスペースの値・ケース名・ファイル
  パスは**その検索で許可されない限り含めない**。「K7 インペラの 3200 rpm での収束挙動」という検索語は、
  結果が何も返らなくても、何を設計中かを外部に伝える。**応答だけ制御して要求を制御しない設計は逆**
- **全リクエストを監査ログに残す**（読める・エクスポートできる）。外に出る通信は `egress` モジュール1つに
  集約したので、「何が外に出るか」のレビュー範囲はディレクトリ1つで済む
- **オフラインは一級の状態**。エラーではない。検索なしでは答えられない問いを名指しした上で、レポートは
  検索なしで生成する
- 検索結果は**取得日付き参考資料**であり、数値の出所にはならない。データと矛盾したらデータを採る（XC-013）

汎用知識は事前資料としても同梱する（レポート作法の要約と出典）。永久に検索を許可されない機械でも、
論拠の土台がある状態にするため。

## API（CT-003）

インターフェースもチャットも外部プログラムも、**唯一のコマンドバス**を通る。25操作のカタログが契約で、
インターフェースにできることは全部ここにあり、ここに無いことはインターフェースにもできない。

- **暗黙の状態を持たない** — 前の結果が要る操作は識別子を引数に取る
- **巨大データは本体に載せない** — 実測で112万点＝圧縮16MB。ハンドルを返して別途取得する
- **エラーは安定ID + 翻訳可能な文言** — サポート会話が引用するのはIDの方

## 数値の正しさを守る仕組み

不変条件として検査で縛っている（`specs/02_invariants.md`）。特に重要な4つ:

- **報告される数値は正準フレーム（m・Z-up）の全データから計算する** — 表示用の形状は間引き・
  分割・拡大されており、それを測ると「正しく見えて間違っている数値」が出る
- **高次要素の線形近似から数値を取らない** — 読み込みでは高次のまま保持されるが、表面抽出・
  等値面・クリップはすべて線形部分セル上で走り、積分の既定も線形。ガウス求積を明示指定する
- **サンプルできなかった点は 0 ではなく欠測** — 埋め込むライブラリの既定は 0 埋めで、
  応力場の「0」は読み手に誤りと分からない。この製品が箱から出して最初に潰す既定値
- **分割ファイルの境界点を二重に数えない** — リーダーは点の統合をしないので、素朴に合計すると
  全界面を重複計上する。小さすぎて気づかず、大きすぎて無視できない誤差

## 型・桁数・精度

数値の正しさは「計算が合っている」だけでは足りない。**型と桁数も結果の一部**である（XC-096, INV-014〜016）。

- 内部計算は **float64**。読み込んだフィールドが float32 なら**有効数字は約7桁**であり、それを15桁で
  表示しても精度は上がらない — 表示が嘘になるだけ。**保存精度を超える桁は出さない**
- 精度の異なるものを混ぜたら**最も弱い方に合わせる**。float32 と float64 を足して倍精度を名乗らない
- **個数は整数のまま**端から端まで運ぶ。要素数・ケース数・点数を浮動小数点で持つと、丸めた瞬間に
  「点が 999999.9999 個」になる
- **物理量を等値比較しない。** 比較には許容差を持たせ、その許容差を記録する

### 大量の数値を言語モデルに渡さない（XC-097）

アシスタントが受け取るのは**メタデータ・計算済みの統計量・テキスト**だけで、生の数値配列ではない。
理由は3つあり、どれ1つでも十分:

- 言語モデルは100万個の数値に対して**算術ができない**。もっともらしい数値を返してくる
- 数値データは**この計算機から出さない**という約束（XC-026）と両立しない
- コストは解析規模に比例して増えるが、そこから得られる価値は増えない

統計量は解析モジュールが正準フレームの全データから計算し、**その値をアシスタントが言葉にする**。
順序が逆になった瞬間、この製品は計測器ではなくなる。

## 色（デザイントークン）

**色は1箇所でしか定義しない**（XC-098）。使用箇所に色を直接書かない。ライト／ダークは同じトークンの
2つの組であり、環境設定で切り替える。

ただし**値を表すカラーマップはテーマの対象外**である。同じ値が2枚のスクリーンショットで違う色に
見えてはならない。欠測値の表現も同様に両テーマで固定。ツールが暗くても、成果物は白背景の技術文書で
あり得る（@Art style は UI テーマと別物）。

## 数値の縮約・ロケール・色

- **要約統計は「縮約方法・範囲・重み付け」を必ず持つ**（INV-017）。既定は**体積重み付き**（点データは
  双対体積）。非構造メッシュの算術平均は、1mm要素と1m要素を同じ重みで数える。どちらも正当だが**別の値**で、
  どちらか言わない「平均」は報告になっていない。この製品が自信を持って間違える最短経路がここ
- **人が読む数値はロケールに従い、機械が読む数値は従わない**（INV-018）。欧州ロケールでは `1.234` が
  千二百三十四になる。CSV/JSON/スクリプトは常にピリオド・桁区切り無し
- **既定カラーマップは知覚均等**（viridis 系）。レインボー/jet も残すが（過去資料と比較できない結果は
  信用されない）、選ぶと**ビューとレポートに「知覚均等ではない」注記が付く**
- **パーツは一級の対象**（INV-019）。ソルバが付けた名前で保持し、個別に表示・選択でき、統計は
  「1パーツか全体か」を必ず明示する
- **表示時刻はグローバル変数**として持つので、パイプラインのループで回せる

## 背景（種類は実装しながら決める）

**どの種類を出すかは実装時に決める**（OPEN-016）。候補は単色・1枚画像・HDRI 環境・3D Gaussian Splatting・
インポート3Dモデルの小道具配置で、この集合自体が変わってよい。

一方で**種類に依らず確定している規則が3つ**ある。①背景は**見た目であって値に触れない**（INV-002。背景を
付けても報告値は1桁も変わらない）②**適用前にコストを提示する**（後から重くなって気づくのではなく）
③**結果ジオメトリを削って背景の場所を空けない**（LIM-009 = 400万プリミティブ）。

規則を Fixed に、リストを Open にしたのは、利用者が頼りにできるのは前者だからである — 「きれいな絵が
別の計測値になっていない」「見栄えのために結果の忠実さが黙って売られていない」。これは splat が採用され
るかどうかに一切依存しない。先にリストを書き下すほうが、根拠の無い部分だった。

## 変数の継承（1変数ごと）

継承は**変数ごとに選ぶ**。「継承」なら子は**編集不可**で親に連動し、「独立」なら子が自分の値を持ち親の
変更は届かない。継承→独立への切り替えは、その時点の値を引き継ぎ、**連動しなくなった旨を明示**する。
子は親に無い変数を**追加できる**が、親が定義した変数を**削除できない**。

以前の版は「上書きされない限り継承」と書いていたが、これだと**離脱が事故になる**。試しに1つ数値を変えた
だけのつもりが、3か月後には親が効かなくなっていて、画面上どこにもそう書いていない。離脱は名前の付いた
操作にした（XC-117）。

## どのケースが表示されているか

3つの成果物領域で規則は同じで、ここは利用者が最も誤解するところなので明記した — **開いているテンプレート
がケースを決める**。テンプレートが何も言わない場合だけ、ツリーで選択中のケースが対象になる。

グラフが5ランを比較する、レポートが2ワークスペースにまたがる、のようにテンプレート側がケースを指定して
いる場合、それらは選択済みとして表示され、**ツリーのクリックでは変更できない**。テンプレートが権威で、
使うケースを変えることはテンプレートの編集である。

## 単位変換に実在のバグがあった（温度）

`units.py` の docstring は「オフセットが要る唯一の量である温度は、専用の変換で扱う」と書いていた。
**その変換は存在しなかった。** 登録されている温度単位は K だけで、誰かが後から `degC` を係数1.0で足した
瞬間、全ての絶対温度が **273.15 K 低い**まま、もっともらしい値として流れ出す。

アフィン変換として実装し直した（`値 × 係数 + オフセット`）。degC / degF を登録。そして重要なのが**もう一段**:

> **10 ℃ は 283.15 K だが、10 ℃ の温度「上昇」は 10 K である。**

差分にオフセットを足すのは、絶対値からオフセットを落とすのと同じ間違いで、**しかも気づきにくい** —
答えがもっともらしい範囲に留まるからだ。この製品が拒否しようとしている失敗の形そのものである。
`convert(..., difference=True)` を用意し、宣言時に**絶対値か差分か**を記録するようにした（INV-028, GL-041）。
degC のオフセットを 0 に戻す変異試験で、テストが落ちることを確認済み。

## モデルに何を教えるか（生成する、書かない）

言語モデルが受け取る「この製品で何ができるか」の説明は、**CT-002 / CT-003 から生成**する（XC-139）。
手書きの一覧は1リリースでコマンド面からずれ、その後モデルが存在しない操作を呼び、**モデルが悪いように
見える**失敗になる。ワークスペースの文脈は要約（ケース木・単位と出所つきの量一覧・テンプレート・状態）
だけを送り、**生の数値配列は送らない**（XC-097）。語彙は用語集のものを使うので、生成レポートの言葉と
画面の言葉が一致する。これは XC-138 の評価セットが意味を持つ条件でもある — 悪化の原因がモデルか
プロンプトに限定され、「黙って古くなった説明」ではなくなる。

## 持ち出し・出力の増加・時刻

- **ワークスペースはパックできる**（文書＋ワークスペース所有のテンプレート・アセット＋任意で入力データ）。
  サイズを提示してから書き、**含められなかったもの**（リンクされた参照フォルダ、再配布不可アセット）を
  名指しする。データ無しのパックを開くと**全ケースが unresolved** になる — 動いているように見せない
- **出力は上書きしないので必ず増える。** 使用量を報告し、**実行単位で古い順に**削除を提案する。削除しても
  実行記録は残るので、**何をどう作ったかは再現可能なまま**（LIM-012 = 20 GB で聞く）
- **記録する時刻は UTC＋その時のローカルオフセット**、表示は読み手のゾーン。2拠点で回した研究や夏時間を
  跨いだ実行記録は、ローカル時刻だけだと順序が決まらない

## 「〜を名指しする」を100回書かない

受入基準の100件以上が「**不足しているものを名指しする**」で終わっている。機能ごとに書けば100通りの微妙に
違う文になり、名指しを省いた最初の1つが次の前例になる。そこで**失敗・拒否の形を1つの契約**にした
（[CT-010](specs/contracts/CT-010_failure_report.md)）: 理由コード／1文の要約／対象（IDと人が分かる名前）／
**何が欠けていたか**／**何か変わったか**／対処／技術詳細。

- **`changed` は飾りではない。** 失敗を読んだ人が知りたいのは「自分のワークスペースは今どうなっているか」で、
  この製品では**ほぼ常に変わっていない**。だが「ほぼ常に」を読み手に推測させてはいけない
- **拒否はエラーではない。** `permissionDenied` や `nameInUse` は製品が正しく動いた結果である。同じ形で
  報告するので、呼び出し側（特にエージェント）が「してはいけない」と「壊れた」を**散文を解析せずに**区別できる
- 出る場所は5つ（要素の横／通知履歴／パイプライン実行記録／コマンド結果／ヘッドレス出力）で**同じ1つの
  オブジェクト**。形を1度覚えたスクリプトが5面すべてに効く

## キーボード体系（約束だけあって中身が無かった）

「全コマンドをキーボードから」と約束し、受入基準が「11_ui.md の体系に従う」と参照していたのに、**その体系は
存在しなかった**。書いた。規則は3つが先: ①**同じ操作はどの領域でも同じキー**（領域を変えても語彙は変わらない）
②**破壊的操作に単独キーは割り当てない**（削除・クリア・破壊的ユニット実行は確認を通す）③**操作対象の場所から
発見できる**。個々のキー割り当てはプラットフォームの慣習に従い、仕様が固定するのは「**何にショートカットが
あるか**」と「**何に与えてはいけないか**」— ゲートが検査するのはその2点で、キーの具体には依存しない。

## 決定が契約に届いていない、を機械で見つける

仕様が腐る一番静かな道は、**決定を書いて、それが変える契約を書き換えないこと**である。ID は全部解決し、
スキーマも全部通り、それでも契約が決定と逆のことを言っている。実際この設計でも手作業で3回見つかった
（`view.create` がケース id のまま／`variable.override` の残存／単位の桁違い）。

そこで検査22を追加した: **決定の日付が、それが `affects:` に挙げた契約ファイルの `updated:` より新しければ
指摘する**。走らせたら61件出て、そのうち大半は「中身は直したのに日付を上げていない」ファイルで、残りが
本物のドリフト（CT-002）だった。日付を実態に合わせ、CT-001/002/003/004/005/006/007 を決定に追随させた。

この検査の弱点も書いておく: **同じ日に別件でその契約を触っていると、日付では隠れる**。だから CT-004/005/006
は中身で突き合わせた — 結果として、ビューがまだ「データセット id」を持っていた（XC-109 と矛盾）、変形倍率も
流線パラメータも成分フレームも保持していない、レポートが複数ワークスペース・出力種別・元データ識別を
持っていない、が見つかった。**機械で見つかる範囲と、読まないと見つからない範囲は違う。**

## 操作カタログは25→45

機能を契約と突き合わせたら、**操作の無い機能**が並んでいた。プローブ、パーツ一覧、派生量、表示単位、
フレーム定義、実測取り込み、タグ提案、テンプレートの昇格・書き出し・取り込み、ライブラリ一覧、
パイプラインの作成・ドライラン・実行・取消、スクリプト実行、納品物の由来照会、監査読み出し、
サポートバンドル。**呼ぶ手段が無い機能は INV-006 を満たせない** — UI が面を迂回するしかなくなるため。

## 結果の種類は「時刻」だけではない

ケースは **結果軸**で索引される（XC-131）: 定常＝なし／過渡＝**時刻**／モーダル＝**モード番号**（各モードが
固有振動数を持つ）／調和＝**周波数と位相角**（複素数）。@Current time step は「その軸上の位置」に一般化した
ので、パイプラインのループが**モードや周波数もそのまま回せる**。

調和解析では **周波数と位相は同時に掃引しない** — 片方を固定してもう片方を進める（ANSYS Mechanical の
Sweeping Phase と同じ）。振幅は `sqrt(実部² + 虚部²)`、位相角 φ での値は `実部·cosφ − 虚部·sinφ` として
派生量カタログに追加した。

**モード番号は時刻ではない。** 「モード3」と「t = 3 s」を1つの軸に並べたグラフは、物理について嘘を言って
いる。軸の異なる結果を1つに載せる場合は、その旨を明示する。

## 変形表示（既定は実スケール）

**既定の変形倍率は 1.0（実形状）**。誇張表示は1操作で出せるが、**倍率は画面と、書き出した画像・動画・
レポートの中に描き込む** — ツールバーだけではない（INV-024）。**計測は常に未変形の正準座標**で行い、
変形形状上での計測は明示要求時のみ・ラベル付き。

ANSYS Mechanical は既定が **Auto Scale**（例: `2.8e+002 (Auto Scale)`）で、倍率はツールバーに出る。それでも
同社のナレッジベースには「変形図が画面下のスケールルーラーと合わないのはなぜか」という質問が**繰り返し**
立っている。**倍率をどこかに出すことは必要だが十分ではない** — 図を測る読み手はツールバーを見ないし、
書き出した画像にツールバーは無い。だからこの製品は1クリック多く払う。

## 流線などの「導出された可視化」

流線・粒子追跡は、**シード・積分法（RK2/RK4/RK45）・初期ステップ幅・最大ステップ数・停止条件**で絵が変わる
（ParaView の Stream Tracer と同じパラメータ群）。これらを View 定義に保持して**同一再現可能**にし、計測値の
横に置かれる時は**「導出された可視化」と明示**する。再現できない線は誰も検証できず、計測値の権威を借りて
しまうため。

## 表示単位・ケース状態・納品物の追跡

- **表示単位は量ごと**に選ぶ（長さ=mm、応力=MPa）。**保存と計算は正準のまま**で、機械可読出力は
  **使った単位をファイル内に明記**する。宣言単位が無い量には表示単位を適用しない
- **ケースは6状態**（unresolved / unloaded / loading / loaded / partial / failed）。UI もパイプラインも
  この状態を根拠に分岐する。以前は各所が独自に「まだ使えない」を判定していた
- **納品したレポートは、その元データの内容識別とワークスペース版を記録**する。定義から再生成できることと、
  **既に送ったファイルが古いかどうか分かること**は別問題だった
- **アシスタントは評価セットで測る**。モデルを変えられる以上（XC-116）、劣化を顧客より先に検出する必要が
  ある。モデル未設定のビルドでは「スキップ」と報告し、**合格とは報告しない**

## 派生量・成分・平均化（互換性のとり方）

**規約は自分で発明せず、この分野に既にあるものを採る。** 別の規則でラベルされた値は、正しくても比較不能に
なるため（[specs/15_derived_quantities.md](specs/15_derived_quantities.md)）。

- 対称テンソルの成分順・名前は **XX, YY, ZZ, XY, YZ, XZ**（2Dは XX, YY, XY）。9成分に標準名は無いので、
  派生量は対称形を要求する
- **主応力は大きい順**（VTK の `vtkTensorPrincipalInvariants` と同じ）。順序は物性ではなく**規約**なので、
  レポートには値の横に順序規則を書く
- 派生量は**カタログ固定**（成分・大きさ・von Mises・主値・主方向・最大せん断・トレース・偏差成分・不変量）。
  式を provenance に保持する。カタログ外はユーザーの式であり、必ず式を表示する
- **成分は必ず「名前の付いたフレーム」で報告**。既定はグローバル直交、円筒・球・ローカルはワークスペースに
  定義して名前参照。解決できないフレーム要求は**拒否**（「半径方向応力」は軸が無ければ量ではない）

### 既定は継承しない — セル→点の平均化

VTK の標準変換は**その点を使う全セルの単純平均**で、絞り込みオプションは**セル次元**で選ぶだけ。材料・
ブロック・パーツは考慮しない。つまり**材料界面で異なる物理の値が1つに混ざり、出力にはその痕跡が残らない**。

この製品はこの既定を継承しない。①**要求されない限り変換しない** ②要求されても**パーツ・材料境界をまたいで
平均しない** ③平均した値は**どこに出ても「平均済み」と表示**。既知の危険と一致させることは互換性ではない
ので、**平均を避けたことを明示**して両者を突き合わせられるようにする。

### 識別子

節点・要素の **global identifier（数値・一意）**と **pedigree identifier（文字列可・一意でなくてよい）**を
そのまま保持する。「最大は節点12345」はソルバ側で確認できるが、「最大はインデックス8412」はどこでも確認
できず、ファイルを書き直せば変わる。**配列位置は識別子ではない**ので、識別子として表示しない。

## 保全と境界

- **変更はジャーナルに追記**し、保存ファイル自体は触らない。異常終了後は未保存作業を提示する
- 同じワークスペースを2つ目のプロセスが開いたら**読み取り専用**で開く（開けない、ではない）
- **undo の境界はワークスペース文書まで。** 書き出したファイルは undo されない — 40ケース分のレポートを
  書き戻すことはできないので、実行記録から**名指しで削除**する導線を用意する
- **実行中はワークスペースの編集をブロック**する（実行対象が足元で動くため）。閲覧はできる
- r1 は**1ウィンドウ**。別モニタへの切り離しはしない。並べ比較はビュー領域の**最大4分割＋カメラ同期**で行う
- アクセシビリティは**キーボード全操作・コントラスト・色相に依存しないカラーマップまでを約束**し、
  **スクリーンリーダーは約束しない**（3D シーンと連続場に意味のある読み上げが無いため）。曖昧に残さない

## 単位

CAE の結果ファイルは単位を持たないのが普通。**この製品はどこからも単位を推測しない** —
ユーザーが宣言するか、「単位未宣言」の印を付けて素の数値として扱うかの二択。
未宣言のまま単位変換を頼まれたら拒否する。
