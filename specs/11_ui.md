# Screens, transitions and shared components

The inventory of what the user sees and how they move between those places. Written at project level
because a screen invented per feature is how the same concept gains a second implementation.

**This file is the first release.** The shell these screens are a subset of - the Window, Screen, Area
and Region grammar, the areas the complete product adds, and the objects behind all of them - is in
[16_application_model.md](16_application_model.md), and the paths a user takes through them are in
[17_user_scenarios.md](17_user_scenarios.md). Where the two describe the same surface, this file
decides what r1 ships and that one decides the shape the surface grows into.

## Layout

One layout, six work areas, one persistent subject. The @Workspace and the selected @Case do not
change when the area changes: **switching area changes the tool, not the subject.**

| Region | Contents |
|---|---|
| top | row one: brand, File/Edit/View/Filter/Tools/Help menus, `Workspace`/`Workspace list` switch, settings and help; row two in a workspace: left-panel toggle, work tools and the workflow tabs in the order Simulation, View, Graph, Report, **Automation**, followed by the global Chat button and right-panel toggle. Chat is a full work area rendering the shared chat but is not inserted into the ordered workflow; Automation is the rightmost workflow tab because it composes and executes the preceding work products |
| left | the @Case tree, variable list and @Reference material in Simulation, View, Graph, Report and Automation; Chat uses the left sidebar for its chat history |
| centre | the searchable current-item selector in the persistent header and **the workspace item currently open**, with the instruction bar along the bottom in every workspace editing area except chat and the dedicated Settings page |
| right | in View, the @Outliner at the top; below it, a vertical icon rail for the current area's editing sections and the selected section |

The top switch names its two destinations **Workspace** and **Workspace list**. It never says `Case
list`: the list's cards are workspaces, and cases remain inside the selected workspace. Opening the
list does not change the active workspace until another card is opened. The panel toggles occupy the
outer ends of the second toolbar as in the retained `cae-saa-s` shell (XC-144), so closing a panel does
not leave its reopen control inside the panel that disappeared. A sidebar never repeats either toggle
in its own header.

Network and audit keeps the workspace shell and its own right rail (workspace/AC-074), because the
permission it edits is per @Workspace (XC-106). It has **no left sidebar**: the case tree, variable list
and reference material are listed above for Simulation, View, Graph, Report and Automation only, and a
case tree beside a workspace-wide permission implies the permission belongs to the selected case - the
same ambiguity XC-165 removed from Settings. Its centre owns the audit records and the permission-state
summary; the right rail owns the controls that change them, and does not restate the summary as
read-only text.

Settings is a dedicated full-width application page rather than a workspace editor. It keeps the global
top navigation and its own internal settings-category navigation, but hides the workspace left sidebar,
right properties sidebar, both sidebar toggles and the natural-language instruction bar. Workspace-scoped
preferences, when present, appear as an explicitly named category inside Settings instead of retaining
case, variable or property panels whose scope would be ambiguous (XC-165).

Chat remains a full work area but is not one of the ordered workflow tabs. Its global button sits in
the right-side utility group, opens the same full-height Chat presentation defined by XC-150, and shows
the selected state while Chat is open. This keeps the workflow sequence unbroken without creating a
second conversation or reducing Chat to a popover. At narrow width its visible label may collapse to
the same accessible icon button; its accessible name and selected state remain available.

Each visible left and right sidebar uses its complete inner boundary as a resize splitter: the left
sidebar's right edge and the right sidebar's left edge. The splitter keeps the ordinary one-pixel
boundary appearance, adds an invisible forgiving hit area, and gains an accent only on hover, keyboard
focus or drag; there is no corner-handle decoration. Dragging it changes that sidebar's horizontal
width; `ArrowLeft` and `ArrowRight` provide the keyboard equivalent. It exposes the WAI-ARIA Window
Splitter semantics: `separator`, vertical orientation, controlled panel, current value and bounds.
Bounds preserve a usable centre surface rather than allowing a panel to cover or collapse it. When
responsive layout hides a sidebar, its splitter is absent. The chosen widths are workspace UI state
and do not change analysis content or the open item's definition (XC-149).

Every non-chat right sidebar uses one compact vertical icon rail at the left edge of its editing region
(XC-146). View keeps the @Outliner full-width above that region. **In every editing area the first section is named after the item it edits** - `ビュー` (`比較` when a
@Comparison is open), `グラフ`, `レポート` - and never `テンプレート`, which remains a reusable-resource
category in the centre-bottom library (XC-149, XC-208). It is not called `全体`: every other tab in
those rails is the whole item as well, so the name drew no distinction and read as the bucket for
whatever had not been given a tab. The three share one icon, because they are one concept. Naming the
first tab after the area's item is the one place the area's own word appears in the rail; the rule
against repeating it forbids prefixing other panels with it, not naming this one. The rail never scrolls horizontally;
its selected icon has both shape and accent treatment, while only the selected section's Japanese name
remains visible in a sticky content header. The header does not repeat the already-selected work-area
name, such as `ビュー`, above `マテリアル`. Every icon has the same accessible name and
hover/focus tooltip, and repeated concepts such as the item section, Text and Output retain one icon and one
relative ordering across areas. **The inverse holds as well: no icon stands for two unrelated
sections**, or the rail teaches a symbol and then contradicts it (XC-208). Material uses a shaded sphere icon in the property rail, material
library category and combined-material preview output; palette and brush symbols remain colour- and
style-specific rather than standing for a material. View divides this one rail into two scope groups:
`ビュー` (`比較`), `カメラ`, `描画`, `背景`, `出力` for the whole View, then a quiet separator followed by
`オブジェクト`, conditional `テキスト`, and `マテリアル` for the active object. The separator is
decorative, hidden from assistive technology and not a focus stop; arrow-key order crosses it normally. Each View icon's accessible name includes
`ビュー全体` or `選択中のオブジェクト`, while its visible tooltip remains the concise tab name.
`ArrowUp`/`ArrowDown` move between tabs, with `Home` and `End` reaching
the ends. The rail borrows Blender's compact property navigation without requiring users to know
Blender's icon vocabulary.

Graph and Report include `出力` as the last tab in visual, DOM and keyboard order (XC-152). It follows the
section before it - Graph `データ`, Report `内容` (XC-208) - with the same ordinary tab gap, and is not
detached at the physical bottom of the rail. The shared
icon, tooltip, selected-name header and keyboard behaviour remain unchanged. Graph Output edits image,
vector and tabular-data export conditions; Report Output edits document format and delivery conditions.
Neither section is a reusable-resource browser.

One centre-bottom **素材ライブラリ** has a shared composition in View, Graph and Report (XC-147,
XC-149). It is separate from the right property editor and provides Template, Object, Material,
Background and user-facing Text categories for Font resources in View; Template, Style and Text in
Graph; and Template, Layout, Style and Text in Report. Immediately below the selected category it places
`サンプル` and `オリジナル` as
two horizontal peer tabs, followed by one primary text-search field, a
  compact `タグ` filter trigger and a compact sort button, then the results. The search placeholder,
empty-state icon and empty-state name follow the selected section rather than always saying Template.
The tag trigger opens a filterable multi-select list of tags that actually occur in the selected
source and scope; selected tags appear as individually removable chips. It never proposes a fabricated
tag. The sort button opens `Default`, `Name: ascending` and `Name: descending`; it does not offer an
order based on metadata the owning contract does not provide. The Tag and sort popovers are mutually
exclusive. Both support pointer and keyboard selection and expose their expanded, option and selected
states to assistive technology (E-085, E-086, E-087). An empty result uses the same restrained
icon-labelled empty or no-match pattern in every library category. Mockup cards represent presentation
resources only and never imply analysis values, source-file metadata or implemented catalogue
provenance. Simulation is a different workflow and has no material library.

Persistent peer tabs use stable equal widths within their own group (XC-168). This applies to the six
top work-area tabs, each View/Graph/Report material-library category group and the two
Sample/Original tabs. Different groups need not share one width. The top group changes to equal-width
icon tabs when labelled tabs do not fit. A library category group keeps its equal readable width and
scrolls horizontally instead of sizing each tab from its label or truncating the label.

The library is docked directly below the centre canvas and directly above the instruction bar, and it
does not consume the right property's vertical span (XC-149). Its top bar is labelled only
`素材ライブラリ` in both collapsed and open states. A compact toggle chevron occupies a dedicated visible
slot immediately after that title rather than at the far end of the row: up means expand while collapsed,
and down means collapse while open. The open-bar hit target and resource-category rail may not cover or
remove that indicator. When open, the resource-category rail shares that same row; the next row combines
Sample/Original with search, Tag and sort before the results. It is
collapsed by default, and the whole collapsed bar is its pointer and keyboard expansion target. The
whole open bar closes it too, except that category tabs and the top-edge resize splitter perform their
named action without closing it. Opening reveals one complete thumbnail row; dragging the full top
edge expands it to multiple complete rows. There is no separate one-row/multi-row icon because it
duplicates the splitter. The open state and height are
remembered per work area in a workspace. At a narrow width, opening it overlays the lower centre canvas
as a bottom drawer above the instruction bar instead of further shrinking the canvas. Chat shows no
material library. A click selects and previews a resource; drag applies it to a target; an explicit
`適用` action provides a non-drag path. The full organiser for import, metadata and bulk library
management remains a distinct future Asset Browser surface rather than being forced into this shelf.
An open material library uses its complete top boundary as a horizontal resize splitter, with the same
quiet boundary, enlarged invisible hit area and interaction-only accent as the sidebar splitters.
Vertical dragging, or `ArrowUp` and `ArrowDown`, changes shelf height in complete-row-compatible bounds.
It exposes `separator`, horizontal orientation, controlled panel, current value and bounds. Its
horizontal width remains the centre column's width: resizing either sidebar changes that width
automatically, avoiding an undocked gap or overlap. Pointer resizing starts from the shelf's rendered
height at pointer-down and follows the pointer delta directly, without height transition or easing, so
the top edge stays under the pointer instead of jumping to a stored expanded height. Its maximum is
derived from the centre column's current rendered height after reserving the persistent work-area and
instruction bars; expanding it therefore shrinks only the centre canvas and never increases the
application's viewport height or introduces application-level vertical scrolling. Collapsing the shelf
hides its splitter (XC-149).

**Workspace artefacts are the subject of the centre; templates are reusable sources** (XC-109).
Simulation, View, Graph, Report and Automation use the same current-item selector in the centre header
for `シミュレーション一覧`, `ビュー一覧`, `グラフ一覧`, `レポート一覧` and `パイプライン一覧`.
The closed control shows the exact open item; opening it reveals substring search, the selectable list
and each item's rename, duplicate and delete menu. Selecting an item switches the centre editor.
The left edge of the shared centre title bar exposes a persistent `編集｜一覧` segmented switch. It
replaces a separate list icon, hover-only control or catalogue close button and never overlays the
canvas. `編集` shows the exact open item in the searchable selector. `一覧` removes that selector and
does not replace it with a redundant `シミュレーション一覧`, `ビュー一覧`, `グラフ一覧`,
`レポート一覧` or `パイプライン一覧` title: the selected mode tab and selected `一覧` segment already
provide that context. Instead, the same title-bar row places catalogue text search, filtering and the
grid/list display switch immediately after the segmented switch; it must not add a second search-toolbar
row. The corresponding saved-item catalogue replaces the centre
editor using the Workspace home list/card language while retaining the bottom instruction bar. During
this catalogue state the right properties sidebar and material library are hidden because they describe
the active editor, not the catalogue. Selecting a catalogue item or activating `編集` restores the
editor and its previous sidebar state.
Creation remains the type-specific primary button at the right edge of the shared title bar rather than
another list row. Its position is identical in `編集` and `一覧`, so changing state never moves the
primary action. The selected
@Case is not an owner: changing case re-renders the same open item unless that
item explicitly binds its own cases. `テンプレートから作成` makes and opens a new independent item;
`テンプレートとして保存` copies the current item into the chosen @Library scope. Neither action creates a
hidden live link, and editing a template never silently changes existing workspace items.

A `シミュレーション` selector entry is one saved flow containing the conditions for one or more
external-solver executions, not one row per solver process (GL-043). Multiple Simulation flows may be
saved, named, reordered and switched inside one Workspace. Simulation produces result Cases only when
its later-release execution is available; Pipeline remains the separate orchestration that may invoke
one pinned Simulation revision and then run View, Graph and Report units over the resulting target set
(XC-154).

The persistent header above the Simulation, View, Graph, Report and Automation canvas identifies the
current workspace item with the shared searchable selector and exposes only the type-specific
`＋ 新規シミュレーション`, `＋ 新規ビュー`,
`＋ 新規グラフ`, `＋ 新規レポート` or `＋ 新規パイプライン` as its primary action (XC-148, XC-155). A generic `＋ 新規作成` label is
not used because it hides what will be created. Simulation still states its later-release availability
and must not claim creation in r1 (XC-091). The header never duplicates `テンプレート` or
`テンプレートとして保存`. Template browsing stays in the centre-bottom material library;
save-as-template remains a secondary command for the selected item rather than permanent header chrome.
Across Simulation, View, Graph, Report and Automation, the selector's small type label is the mode name
(`シミュレーション`, `ビュー`, `グラフ`, `レポート`, `自動化`) rather than a redundant `現在の...` form.
The selected item name directly below already identifies the current saved item (XC-156, XC-157). The
selected name remains the workspace item's exact name, such as `標準ビュー` in the mockup; a saved
automation item continues to use the `パイプライン` type name in its selector.
The selector is rendered as one bordered combo button: its compact kind label (for example `ビュー`),
the selected item name (for example `標準ビュー`) and the chevron are one visual control. The kind
label and an accessible name such as `ビューを選択` make it clear that the item title and chevron are
bound to the same switching action (XC-162). Hovering or keyboard-focusing a View or Graph option
reveals a nearby still preview of that saved item; the preview is a visual aid only and never claims
to contain live analysis values. The preview is rendered outside the option list so the list never gains
horizontal scrolling; the option list itself scrolls vertically when needed. Simulation, Report and Automation options remain compact until their
own preview semantics are defined (XC-163).

The instruction bar and Chat mode are two presentations of one active conversation, never separate
assistant features or histories (XC-150). The centre-bottom bar is its compact composer and current
status in every non-Chat work area; Chat mode is the full-height rendering of the same ordered messages,
responses, confirmations, failures and activity. A submission from either surface is appended once to
the same conversation and reaches the same command surface as the interface does (INV-006). Switching
between them preserves the active conversation, draft, pending response and conversation settings.
The instruction bar is absent in Chat only because the same composer is rendered inside the full-height
conversation there.

In a non-Chat work area, opening the compact instruction bar reveals that conversation as a dismissible
right overlay drawer inside the central work surface, immediately left of the right properties sidebar
(XC-151). The properties sidebar remains visible and keeps editing the current item or selection. The
drawer overlays the canvas rather than adding a permanent fourth column; the material library remains
docked below the canvas. While the drawer is open, the compact input is absent and the one shared composer
is at the drawer bottom. Closing it restores the compact input with the draft unchanged. `チャットで開く`
uses the full-height Chat presentation without copying, replaying or resetting the conversation. At a
narrow width the drawer may use the full central-work-surface width, remains dismissible and cannot cause
application-level horizontal or vertical scrolling.

**Empty and error states are columns, not afterthoughts.** They are the states a user meets first and
most often, and the ones no demonstration ever shows.

## The 3D viewport mock

The design mockup's populated View states render an interactive **Three.js** placeholder derived from
the retained `cae-saa-s` viewport composition (XC-144). Every pane in the one-, two-, three- and
four-pane variants has orbit and zoom interaction, zoom-to-fit, optional auto-rotation, surface,
surface-with-edges and wireframe modes, a ground grid and an orientation gizmo. Narrow split panes
reduce overlay text before hiding the canvas or its controls.

The upper-right viewport cluster follows the convention shared by Blender and other major 3D tools
(XC-145): representation controls occupy the first row, and the interactive XYZ orientation gizmo is
right-aligned immediately below them. It never falls back to the lower-right corner or overlaps the
representation controls, including in split panes. Its diameter is reduced for the compact viewport
chrome only as far as readability allows: the axis-head circles and their `X`, `Y` and `Z` letters
remain visually prominent, while a visible gap remains below the icon row and no head is clipped. X
is red, Y green and Z blue, and each axis head carries a clearly legible label at browser-default zoom.

This is a design instrument, not the product renderer selected by XC-044. Its mechanical assembly is
visibly labelled as temporary and disconnected. It carries no simulated field, result legend, value,
unit, source-file name, coordinate-system claim, cell count or provenance. Clicking a part identifies
only the mock part. Empty and renderer-error variants retain their explicit states instead of showing
a plausible 3D result. The Canvas fills both its pane and the centre display region without inheriting
the generic canvas wrapper's padding, light background, scrolling frame or a separate status footer;
the in-viewport mock label is sufficient.
Panel and material-library resizing changes only the viewport bounds; it does not remount the 3D scene
or refit the camera. The camera pose, orbit target and current result position remain stable while the
canvas is resized (XC-161).

## The left sidebar

The sidebar begins directly with its usable navigation: the same permanent case search in Simulation,
View, Graph, Report and Automation. Chat uses the sidebar for its chat history; it has no
`Workspace`/`Conversation` title row and
no adjacent add button. The entire shell already represents the open @Workspace; creating another one
belongs to the **New workspace** action in Workspace list, not to navigation inside the current
workspace.

- **Cases** - the @Workspace hierarchy, selection, tags, filtering. Selecting a @Case changes the
  subject of every area at once. At the scale this product allows (LIM-005) the tree carries

  a five-hundred-case study fully expanded is a list nobody can navigate

- **Variables** - one list holding declared values, fields read from data, and computed quantities,

- **Reference material** - documents and linked folders the assistant may consult, never a source of

## The right sidebar

Per area, with the working items of that area above the tabs that edit them. View alone places the @Outliner
above both. Every tab's contents can be applied by dragging onto the centre as well as by selecting in
the sidebar. The sidebar begins directly with its tabs, except that View begins with the Outliner. It
does not repeat the active mode in a generic `Simulation items`, `Graph items`, `Report items` or
equivalent heading. The only right-panel control is at the far right of the work toolbar.

### Outliner

The View area's right sidebar begins with the @Outliner. It presents the selected @Dataset as a dense
tree following Blender's established Outliner grammar (XC-143, E-079), using the shell's light neutral
panel colours rather than importing Blender's dark theme (XC-144):

- one row per source data element, with indentation and guide lines showing containment
- a disclosure triangle only when the row has children; opening and closing never changes data
- a type icon followed by the exact name carried by the source file
- the selected row synchronized with selection in the active viewport
- a right-edge visibility toggle on every displayable row; `Shift` applies it to descendants and
  `Ctrl` isolates that branch, with the affected rows previewed before a large recursive change
- a header titled `Outliner`, followed by substring search and a filter menu; the actual dataset root
  name is the first tree row, so the header has no static `Dataset` type button

At browser-default zoom in the design mockup, source names use the type scale's **emphasis** step in
27 px rows rather than its body step, which the rest of the panel's metadata uses. The step is named
rather than measured in pixels because a literal here is a literal the scale cannot move (XC-201). The panel remains compact, but its light-neutral surfaces are
layered: a slightly darker header, a quiet tools strip and a near-white tree. A selected row uses a
pale blue surface plus a left accent, so selection does not depend on text colour alone. There is no
persistent shortcut footer for `Shift` or `Ctrl`; those interactions remain available without taking
tree space. This is the SOLVIA shell palette, not Blender's dark theme (XC-144).

The tree preserves only hierarchy present in the analysis file. Flat source elements remain siblings
under the dataset root; absent names remain explicitly unnamed; neither names nor parentage are
inferred. With no loaded dataset the panel is an empty state, not a sample tree. An unreadable or
partial structure names what could not be read and shows only confirmed nodes. r1 does not rename,
reparent or delete source elements from the Outliner: it is an inspection, selection and visibility
surface, not geometry authoring.

### View object taxonomy

The View Object section and the View Outliner use the following first-release display taxonomy. The
taxonomy follows Blender's separation of Mesh, Curve, Text, Volume and point-based objects, but names
CAE-specific roles explicitly so that source data, derived visualisations and decorative effects cannot
be confused:

`View object` means the current selectable instance owned by the open View. `Asset` is reserved for a
reusable resource in the material library, with scope, revision, origin and import/export lifecycle.
An Object asset in the library creates an independent View object when applied; the source @Dataset
remains separate and is never renamed or converted into either one (GL-018, GL-044, XC-166).

- **解析メッシュ** - the analysis mesh or surface carrying solver-linked results; it preserves source
  identity, element/point selection and provenance
- **参照メッシュ** - CAD, surrounding geometry, comparison geometry or a background shape; it is a
  display role of the same Mesh family, not a separate file format
- **スカラー場** - colour-mapped scalar results such as stress, temperature or pressure, including
  contours and isosurfaces; values and units remain linked to their source dataset
- **ベクトル場** - directional results such as displacement, force or velocity shown with glyphs or
  oriented segments; magnitude, direction, units and sampling are explicit
- **流線・軌跡** - derived curves for streamlines, pathlines and particle trajectories; generation
  method, seed set, time range and source field are recorded
- **点群** - measured points, particles, sensors or other discrete samples; point attributes and
  coordinate provenance remain distinguishable from a continuous mesh
- **テキスト・注釈** - labels, dimensions, callouts and explanatory notes anchored in screen or world
  space; annotation content is never presented as solver data
- **エフェクト** - optional particles, glow, highlight and other decorative or emphasis layers; effects
  never invent analysis values and are clearly marked as display-only

`Mesh` is therefore classified by role (`解析` or `参照`) rather than duplicated as two technical
object types. `ベクトル場`, `スカラー場` and `流線・軌跡` are result representations, not replacements
for the source dataset. The first release does not add a separate volume, camera, light or image object
category; volume rendering, reference images and scene helpers remain future extensions after their
provenance and editing semantics are specified. Object creation and editing must fail closed when the
required source field, units, coordinates or provenance are missing.

Below the Outliner, each section is named for the current state it edits. There is no generic `View objects`
heading: it adds no information above tabs already named Overall, Rendering, Objects, Materials,
contextual Text, Background and Output. These sections use the shared vertical icon rail of XC-146; the
Outliner itself remains full-width and is not squeezed into the rail's content column. These tabs never
contain Sample/Original, search, tag, sort or reusable-resource results: they inspect and edit the
current whole item or current selection (XC-149).

## Comparing: a session split, and a saved comparison

Two mechanisms, separated by what the user is doing (XC-202).

**Splitting** the canvas into one to four panes is **session state**. Nothing about it enters the @View
definition, and nothing about it appears in the property rail - a document editor holding a session
control is the confusion this decision removes. Its controls are placed by what they are (XC-204): the
pane count and camera synchronisation are **in the work area bar**, in one menu behind a single icon,
because they describe the layout the bar sits above rather than the picture; each pane's @Case and
camera are **on the pane**, named on its badge, because they describe that picture. **That menu is one
control for one question - how this canvas is laid out - and it does not disappear between the two kinds
of View item** (XC-206): on a @Comparison it sets the column count instead, and says that the pane count
is the member count. It is absent only where there is no canvas of panes: an overlaid comparison, and
every area that has no panes.

**The 3D canvas carries no split chrome at any pane count** (XC-209). What a split adds beyond the
layout menu is two facts, and both are in that menu, shown only while the canvas is divided: that the
split is session state and is not saved, and the single action `この比較を保存`. Everything a strip on
the canvas would otherwise repeat is already elsewhere - the pane count and the way back to one pane are
the menu's own items, the camera synchronisation is a checked item in it, and each pane's @Case and
camera are on that pane's badge, which is a dropdown trigger and so needs no sentence saying it can be
clicked. **A split is not an export path** (XC-210). It divides what is on screen while the user works; the
output tab writes the one camera it names, and while the canvas is divided it says so, because that tab
is where a user expects the side-by-side they are looking at. The route to a multi-pane deliverable is
`この比較を保存`, which asks the only question the split cannot answer - which axis was being varied -
and creates the item below, with the shared colour map and the reproducibility that a figure needs.

**A @Comparison is what a multi-pane image, video or @Pipeline output is made from** (XC-212). Its own
`出力` tab writes the whole grid, and it does not ask again for the camera or the result position: each
is either the axis being varied or the shared binding named in `比較`, so the tab reports which, and a
second control that could disagree with the definition never exists. A comparison whose axis **is** the
@Result axis cannot be a video - every pane is pinned to its own position, so there is nothing left to
play - and the tab says that rather than writing a still sequence; over any other axis the panes advance
together along the shared position. A @Pipeline unit that produces a @View, @Graph or @Report **names
the item it produces**, a comparison among them, and refuses to run until it does (XC-211).

A **@Comparison** is the second kind of item in the View area, created from the same
`＋ 新規ビュー` action, which offers `単一` and `比較`. Its definition names a base @View and varies
**exactly one** axis over an ordered list of two or more members:

| Axis | Members | Everything else |
|---|---|---|
| @Case | cases from the tree, or a saved selection (CT-007) | shared: one camera, one result position |
| @Result axis position - time, mode number or frequency (XC-131) | saved result positions picked one by one, **or** a from/to range divided into a stated number of members | shared: one case, one camera |
| camera | cameras saved on the base @View | shared: one case, one result position |
| a published property of the base @View | values of that property: the coloured quantity, the @Deformation scale, the representation, a slice's placement | shared: everything else, including the property's siblings |

It carries no objects, materials, lighting, background or guides of its own; every one of them comes
from the base @View, so a comparison is edited by editing that View - and even the varied property is
one of that View's own, which is why the guarantee holds. Its own controls live in one `比較` group in
`比較`: the base View, the axis, the member list, **the bindings for the axes not chosen** - which
single @Case, camera and result position every pane uses - the arrangement, the label template and the
colour-map rule. "Everything else is shared" is only checkable when the shared values are written down.
The rail does not gain a tab, and a single View never shows the group.

**The rail keeps its full set of tabs for a comparison and marks the borrowed ones.** `比較` and `出力`
are the comparison's own; `カメラ`, `描画`, `背景`, `オブジェクト`, `テキスト` and `マテリアル` belong to
the base @View, and each says so with the way to edit it there rather than offering an editable copy
(XC-182). The @Outliner likewise presents the base View's structure and says whose it is. Removing the
borrowed tabs would leave "where did the material go" unanswered on screen; leaving them unmarked would
make a reader open six tabs to find the two that can be edited.

A saved result position is **made on the axis it indexes**: the playback overlay's bookmark panel keeps
the position currently scrubbed to, or takes a rule - an extremum of a quantity, a threshold crossing,
or the axis end - and names it. Nothing else creates one, because a position invented away from the
axis has nothing to resolve against. A steady @Case therefore has no overlay and no saved positions.

**The arrangement of a grid is the comparison's own property, not a session layout** (XC-205), which is
why the area bar's split control is absent on a comparison: its panes are its members. The **column count only** is chosen - `自動`, or one to four -
and the row count always follows from the member count, so no setting can produce a grid that leaves a
member undrawn. It is chosen in the work area bar's layout menu, the same control a single @View uses to
split (XC-206), and the rail reports the row and column it resolved to rather than offering a second
control for the same value. `自動` keeps the members on one line and
wraps only when they no longer fit, because the reading order is the axis being varied. The canvas is
laid out from the same rule the rail states.

A generated member lands on a position that exists on the axis and says when it snapped; two members
that snap to the same stored position are reported rather than drawn as two identical panes. Dividing a
range is how a contact sheet over time is made without first naming every position as a bookmark.

**Several saved Views are never the members.** Two panes drawn from two Views may differ in materials,
lighting, colour map and camera at once, so the reader cannot say what caused the difference - which is
the one thing a comparison exists to show. That case is the split, whose export says it is a capture of
a layout. **The reference to the base View is live**, unlike a @Template (XC-109): editing the View
changes every pane, and deleting it names the comparisons that point at it before it happens, leaving
them unresolved rather than repointed (XC-062).

Arrangement is one switch, not two features: **grid** of a stated number of rows and columns, or
**overlay** in one picture. In overlay at most one member may carry result colouring and the others are
drawn as reference geometry, because two colour-mapped fields in one picture encode nothing (XC-203).

Every pane is labelled with its member. Every member resolves its colour through one colour map and one
range; where that is impossible the figure states it per pane and the export repeats the statement
(XC-203). Two axes at once are refused: the request is two nested comparisons, and one panel holding a
matrix of members is the panel nobody can read.

## Which cases an area is showing

The rule is the same in all three artefact areas: **the open workspace item decides the cases when it
contains an explicit binding; otherwise the case tree supplies the selected case.**

- with no case selection of its own, the open item renders the **selected @Case** from the tree
- where the item's own settings name cases - a graph across five runs, a report over two
  workspaces - those cases are shown as selected and **the tree selection cannot override them by
  clicking**. The item is the authority; changing which cases it uses is an edit to that item
- a @View additionally applies to whatever mesh the case has: fields it cannot find are listed as
  unresolved and the rest is drawn (XC-090), and a @Graph draws a case missing a quantity as no data
  rather than dropping it from the legend

## Three surfaces that are easy to leave undefined

- **Pipeline nesting.** A loop, a condition and a simulation unit are drawn as a **bounded zone** around
  the units they contain, not as indentation, because indentation at three levels stops reading as
  containment. A drop position is previewed as a line before the drop, and every unit carries the count
  of cases it will act on.
- **A run in progress.** Progress lives in the top bar, visible from every area. Viewing continues;
  **editing the workspace being run against is blocked** with the reason stated (pipeline/AC-040), because
  the run's subject would move underneath it. Cancelling stops at a unit boundary.
- **Where failures appear.** A failure is shown **where it happened** - on the unit, the case, the pane -
  and is also kept in a notification history, so a failure during a long run is not lost by looking away.
  Neither surface replaces the other: the inline one is how it is noticed, the history is how it is found
  again.

## State transitions

### XC-060 - What may interrupt what
- statement: loading a @Dataset, rendering, and exporting are cancellable and never block the case
  tree or the instruction bar; a second load of the same @Case supersedes the first rather than
  queueing; an export in progress blocks a second export of the same target and says so
- decidedness: Fixed
- basis: E-001 (T1)

### XC-061 - Undo
- statement: every state change **to the @Workspace** made through the interface, the instruction bar,
  the assistant or a script is undoable as one step, including multi-part instructions, which undo as a
  unit. **Files already written are not undone** - a pipeline run that exported thirty reports cannot
  unwrite them, so undo restores the workspace and the run record offers to delete what it produced,
  naming the files
- correction: an earlier version said simply that every state change is undoable as one step, which a
  forty-case run that writes to disk cannot honour. The boundary is the workspace document; beyond it,
  the product offers deletion rather than pretending to reverse
- rationale: the assistant applies several changes from one sentence; undoing them one at a time is
  not undo, it is archaeology
- decidedness: Fixed
- basis: E-001 (T1)

### XC-062 - Confirmation
- statement: operations that overwrite a file, delete a @Case, or change an inherited @Variable for
  descendants require confirmation naming what will change and how many places it affects
- decidedness: Fixed
- basis: E-001 (T1)

### XC-063 - Applying a template
- statement: applying a @Template shows what resolved and what did not before anything is drawn; after
  acceptance it creates a new independent workspace item, and the unresolved list plus source template
  identifier and revision stay reachable from that item (XC-090, XC-109)
- decidedness: Fixed
- basis: E-088 (T1)

## The keyboard scheme

"Every command is reachable from the keyboard" was a promise with nothing behind it: an acceptance
criterion pointed at a scheme that did not exist, so nothing could be checked and every panel would
have invented its own. The scheme is here, and the gate of XC-127 checks commands against it.

**Three rules first**, because they decide the rest:

- **the same action has the same key in every area.** Switching area changes the subject, not the
  vocabulary
- **nothing destructive has a single-key shortcut.** Deleting a @Case, clearing a @Target set and
  running a destructive @Pipeline unit are reached through their confirmations (XC-062, XC-094)
- **every shortcut is discoverable from the thing it operates on** - shown beside the action in menus
  and in the command list - because a shortcut nobody can find is a shortcut nobody uses

| Group | Keys | Notes |
|---|---|---|
| workspace | new, open, save, save-as | the platform's standard modifiers |
| undo and redo | undo, redo | one instruction, one step, including a whole script (XC-061) |
| areas | one key per area: simulation, view, graph, report, **automation**, chat | the subject does not change. Six areas, six keys - an earlier version of this row listed five and omitted Automation, which is the area whose commands are least reachable any other way |
| case tree | up and down to move, left and right to collapse and expand, type to search | search is the permanent control, not a dialogue |
| outliner | up and down to move, left and right to collapse and expand, type to search, visibility toggle, isolate branch | affects the active View; never edits source hierarchy |
| result axis | play/pause, step back, step forward, first, last | the same keys whether the axis is time, mode or frequency (XC-131) |
| view | frame the model, standard orthographic directions, toggle deformation between 1.0 and the chosen factor | the deformation toggle is why the factor is always drawn (INV-024) |
| selection and probe | probe at cursor, keep the probed value as a @Variable | keeping is deliberate, never automatic |
| instruction bar | focus it from anywhere; escape returns focus where it was | this is the path an agent-assisted user takes most |
| panels | show or hide the left and right sidebars, enter and leave the split layout | |

**The exact key for each is a platform decision, not a specification one** - the platform's own
conventions win, and this table fixes *what has a shortcut* and *what may not have one*. What the gate
checks is coverage and the destructive-key prohibition, neither of which depends on which key it is.

## Conventions

- layout and spacing: one spacing scale, applied everywhere; density suited to a technical tool used
  for hours, not to a marketing page
- **type: one scale, applied everywhere** (XC-201). Six size steps - caption, body, emphasis, title,
  heading, display - two families, two weights, four line heights and two letter-spacings, each a named
  token in the same two layers as the colour tokens. No rule sets a size of its own, a component
  library's own type is replaced rather than inherited, and the typeface of the deliverable is a
  separate named token from the shell's
- typography and colour: every colour is a named token, and light and dark are two sets of the same
  tokens, switched in settings (XC-098). No colour is written at a use site. Numbers are set in a font
  whose digits align in columns, because tables of results are read by comparison, and are shown to the
  significant digits the data supports (INV-014). Contrast holds to the level committed in XC-022,
  verified against the colour maps on screen rather than against a white page
- **colour maps are not themed**: a map encoding values looks the same in light and dark, because the
  same value must not look different in two screenshots of one result
- interaction: every command reachable from the keyboard; focus order follows reading order; anything
  that changes the @Workspace is undoable as one step, while files already written are deleted rather
  than undone (XC-061)
- accessibility: keyboard operation, the contrast level of XC-022, and colour maps readable without hue
  alone are committed; **screen-reader support is not** (XC-114), and the product says so rather than
  implying it
- numbers: displayed values follow the interface language; machine-readable output never does (XC-110)
- the interface's own theme is separate from @Art style: the tool may be dark while the deliverable is
  a white-background engineering document (GL-013)

These live here rather than in a feature spec: written per feature they diverge, and the divergence is
visible to the user as an interface assembled by different people.
