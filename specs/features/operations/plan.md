# Plan: running the product

- approach: three concerns that share one property - they are all about what the product does when
  nobody has configured it. First run, diagnosis, and the gate that keeps the command surface honest
- modules touched: MOD-009 app-shell, MOD-014 egress, MOD-012 command
- contracts touched: CT-002 and CT-003, as the subject of the coverage gate
- technology: the sample workspace's data is generated by the same writers the test fixtures use, so it
  ships without third-party terms (XC-085)
- risks: the coverage gate is the one that can pass vacuously. A gate that finds no interface code and
  reports success is worse than no gate, because it is believed

## Order of work

1. the coverage gate over CT-002 and CT-003, reporting what it could not check (REQ-004)
2. the generated sample workspace, and first run opening a View on it (REQ-001)
3. logs without field values, and the support bundle with its manifest (REQ-003)
4. the tutorial over the real interface (REQ-002)
5. sample updates that never overwrite copies (REQ-006)
6. authentication for the headless form, when that form exists (REQ-005)

The gate comes first deliberately: it is the cheapest of these to build and the only one that gets
harder the longer the product exists.

## What must be proven before this feature is called done

- the gate fails when an operation is added to one contract and not the other, proven by adding one in
  each direction
- a first launch with no configuration reaches a rendered result
- a support bundle's manifest lists every case name and path it contains, before it is written
