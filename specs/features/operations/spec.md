# Feature: running the product

## Users and purpose

- intended user: everyone who starts the product, and the person who has to support them
- job to be done: get from a first launch to a working view without a manual, and get a problem
  diagnosed without sending a customer's geometry to a stranger
- success condition: a new user reaches a rendered result on first run; a support request carries what
  is needed and nothing the user did not agree to send

## Out of scope

- automatic crash reporting: nothing leaves the machine without a person deciding (XC-126)
- a plugin system: the extension seams are the ones in [../../01_boundaries.md](../../01_boundaries.md)

## Files and interfaces involved

- MOD-009 app-shell, MOD-014 egress, MOD-012 command, MOD-013 scripting
- the layout and keyboard scheme of [../../11_ui.md](../../11_ui.md)

## Requirements

### REQ-001 - First run opens a View, not a file dialogue
- priority: MUST
- phase: r1
- decidedness: Bounded
- acceptance:
  - AC-001: When the product starts for the first time, the system shall open the **View** area showing
    either a shipped sample @Workspace or an empty one, offering the sample first (XC-129)
  - AC-002: When the sample workspace is opened, the system shall use data generated by this project
    rather than third-party result files, so that it may be shipped (XC-085)
  - AC-003: If the user chooses the empty workspace, then the system shall still open the View area with
    its empty state and a drop target, rather than a dialogue

### REQ-002 - A tutorial that points at the interface
- priority: SHOULD
- phase: r1
- decidedness: Bounded
- acceptance:
  - AC-004: When the tutorial runs, the system shall point at the control to use next **on the real
    interface** and shall advance when the user uses it, not on a timer
  - AC-005: When the tutorial is dismissed, the system shall record where it stopped and shall offer to
    resume it later
  - AC-006: If the user does something other than the suggested step, then the system shall let the
    action happen and shall re-point rather than blocking it

### REQ-003 - Logs are local, and a support bundle is assembled in the open
- priority: MUST
- phase: r1
- decidedness: Fixed
- basis: E-001 (T1)
- acceptance:
  - AC-007: When the product writes a log, the system shall write it locally and shall include no field
    values (XC-126)
  - AC-008: When a support bundle is requested, the system shall list everything it will contain -
    including case names and file paths - before creating it
  - AC-009: If a support bundle would leave the machine, then the system shall require explicit consent
    and shall record the transfer in the outbound audit (XC-106)

### REQ-004 - Every command is reachable, and that is checked rather than claimed
- priority: MUST
- phase: r1
- decidedness: Fixed
- basis: E-001 (T1)
- acceptance:
  - AC-010: When the product is built, a gate shall assert that every operation of CT-003 appears in the
    command surface of CT-002 and that no operation exists in one and not the other (XC-127)
  - AC-011: When the interface gains an action that changes state, the gate shall assert that it
    dispatches a command rather than mutating state directly (INV-006)
  - AC-012: When the gate runs, it shall report what it checked **and what it could not**, so that an
    unimplemented half never reads as a pass
  - AC-013: Where a command exists, the system shall provide a keyboard route to it, following the
    scheme in [../../11_ui.md](../../11_ui.md)

### REQ-005 - The headless product authenticates before it acts
- priority: MUST
- phase: later
- decidedness: Fixed
- basis: E-001 (T1)
- acceptance:
  - AC-014: When a caller connects to the command-line or hosted form, the system shall require
    authentication and shall refuse an unknown caller by default (XC-128)
  - AC-015: When a caller is authorised, the system shall authorise per @Workspace rather than per
    installation
  - AC-016: When any operation runs, the system shall record the identity that issued it in the audit
  - AC-017: Where the caller is an autonomous agent, the system shall grant it no implicit trust beyond
    the identity it authenticated with

### REQ-006 - An updated sample never overwrites somebody's copy
- priority: MUST
- phase: r1
- decidedness: Fixed
- basis: E-001 (T1)
- acceptance:
  - AC-018: When an update ships a changed sample, the system shall add the new version alongside and
    shall leave copies the user made untouched (XC-130)
  - AC-019: Where a copy records a sample as its origin, the system shall show that a newer version
    exists, and adopting it shall be the user's action

### REQ-007 - Latency has budgets, measured before they are promised
- priority: SHOULD
- phase: r1
- decidedness: Open
- open: OPEN-017
- acceptance:
  - AC-020: When the product launches on the sample @Workspace, the system shall reach a rendered result
    within LIM-010
  - AC-021: When a @Case is selected, the system shall reflect it in every area within LIM-011

### REQ-008 - A shared component has one implementation
- priority: MUST
- phase: r1
- decidedness: Fixed
- basis: E-001 (T1)
- acceptance:
  - AC-022: When the build runs, a gate shall assert that each component named in
    [../../11_ui.md](../../11_ui.md) exists once, in the module that owns it (XC-015)
  - AC-023: If a second implementation of a named component appears, then the gate shall fail and shall
    name both places
  - AC-024: When the gate cannot examine the interface - no interface code yet - it shall report that,
    rather than reporting that the components are unique

### REQ-009 - One failure shape, on every surface
- priority: MUST
- phase: r1
- decidedness: Fixed
- basis: E-001 (T1)
- acceptance:
  - AC-025: When anything is refused or fails, the system shall report it in the shape of CT-010 - a
    reason code, what it happened to, what was missing, and whether anything changed
  - AC-026: When a failure is shown to a person, the system shall put no internal path, stack or
    identifier in the summary, and no field value in any log line (XC-126)
  - AC-027: If an operation is refused rather than broken - a permission, a name in use - then the
    reason code shall come from the refusal group, so a caller can tell the two apart without parsing
    prose
  - AC-028: When a headless run ends, the system shall exit non-zero for any failure outside the
    incomplete group, and zero where the only reports were partial results

## End-to-end verification

Start the product with no configuration: it opens the View area on the sample workspace with a rendered
result, and the tutorial points at the first control. Dismiss it, reopen it, and confirm it resumes.
Request a support bundle and confirm it lists case names and paths before creating anything and that
nothing leaves the machine without consent. Run the build gate and confirm it names both what it checked
and what it could not check.
